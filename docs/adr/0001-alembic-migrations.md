# ADR-0001: Adopt Alembic for schema migrations; keep create_all as dev convenience

Date: 2026-09-18
Status: Accepted
Supersedes: none
Related: AUDIT A-28, docs/STATUS.md "Known open items", docs/design.md §6

## Context

Until now the schema came from `Base.metadata.create_all` at startup
(EVALUATION limitation 1). That works for a fresh database and never lies
about the models, but it cannot change an existing database: adding or
altering a column requires manual SQL against deployed SQLite/PostgreSQL
files. The 2026-09-14 audit recorded this as A-28 (Infra) and deferred it
with a six-step adoption plan rather than shipping a half-configured tool.

Two constraints shaped the decision:

- The models in `models.py` are the source of truth; migrations must be
  derivable from them, not hand-written beside them.
- The app must keep working keyless and zero-config on first run
  (`uv run uvicorn main:app` against an empty directory).

## Decision

1. **Adopt Alembic** as the canonical schema-change path. `migrations/env.py`
   is wired to `models.Base.metadata` and `settings.DATABASE_URL` (async
   recipe: `async_engine_from_config` + `connection.run_sync`), so the URL
   and secrets stay in the settings layer and never appear in migration
   scripts.
2. **Baseline revision autogenerated from the models** against an empty
   database, then reviewed op by op before committing.
3. **Startup policy: keep `create_all` in the lifespan, run migrations for
   real changes.** Rationale: `create_all` is a no-op on an up-to-date
   schema and makes `git clone && uv run uvicorn main:app` work with no
   extra step; dropping it would trade a real convenience for purity. Any
   change to existing columns/tables/constraints lands as an Alembic
   revision: `create_all` cannot produce those, and the revision chain is
   the only path a deployed database follows. This split is documented in
   docs/design.md §6 and ARCHITECTURE.md.
4. **CI gains an `alembic upgrade head` smoke step** (fresh SQLite file →
   upgrade → assert tables exist), so a broken migration chain fails the
   build rather than a user's deploy.

## Alternatives considered

- **Drop `create_all` entirely** (migrations only). Rejected: breaks the
  zero-config first run for no safety gain; the no-op behavior on current
  schemas is well-defined.
- **Keep create_all only, no Alembic** (status quo). Rejected: this is the
  A-28 defect; deployed schema changes stay manual and error-prone.
- **Startup `alembic upgrade head` inside the lifespan.** Rejected for now:
  it couples app boot to migration state, surprises in multi-worker setups
  (racing upgrades), and hides a schema operation inside a web request path.
  The explicit command (or release step) is auditable. Revisit if a
  single-binary deploy story emerges.
- **Raw SQL migration folder without Alembic.** Rejected: loses
  autogenerate-from-models, downgrade paths, and revision lineage, the
  exact conveniences that keep the chain honest.

## Consequences

- `alembic` joins the main dependency group; `uv run alembic upgrade head`
  becomes the documented upgrade step for existing deployments.
- Model changes without a matching revision now leave the chain stale; the
  CI smoke step and the testing style guide make the expected workflow
  explicit (revise → upgrade → downgrade round-trip → tests).
- SQLite's limited ALTER support means some future changes will need the
  batch mode; revisions should prefer `op.*` operations that Alembic can
  reverse.
